# QCS v11.2.2 — The update check stops depending on the machine

> **PATCH** release (v11.2.1 → v11.2.2): fixes the update check on machines
> whose certificate store is not current, and makes every failure state its
> reason. No new features and no change to qualification results.

## The failure

A field notebook with working internet answered *"The releases page could not
be reached - no connection, or GitHub is unavailable"*. Both halves of that
sentence were wrong, and the app had no way to know: `fetch_latest` caught
**every** exception and returned `None`, so DNS, a proxy, a timeout and an
expired certificate all collapsed into the same message.

The cause is a Windows detail with real consequences for field machines.
`api.github.com` chains to **Sectigo Public Server Authentication Root E46**, a
recent root. The browser and PowerShell can fetch a missing root on demand;
**Python validates only against the roots already installed**. A notebook that
is rarely online — precisely the machine this program is packaged for — can
simply not have it, and then the check fails while everything else works.

## The fixes

- **The app carries its own CA bundle** (`certifi`, 118 roots), used by both
  the check and the installer download. It no longer depends on the target
  machine's certificate store. Without `certifi` (running from source) it
  falls back to the system context, so nothing breaks.
- **`fetch_latest` raises instead of swallowing.** The silent-on-startup
  policy moved to the call site, where it belongs: the startup check stays
  silent (and logs the reason), the manual *Help → Check for updates…* now
  names the cause — an unverifiable certificate, a DNS failure, a timeout, an
  HTTP status — and, for the certificate case, says that Windows updates
  usually fix it.
- **Timeout raised from 6 s to 15 s.** A cold TLS handshake over a slow field
  link can spend several seconds before the first byte, and a short timeout is
  indistinguishable from "no internet" to the user.

## Verification

51 self-tests (one new), ruff clean. The decisive check was run against the
live API with the **Windows certificate store excluded**: trusting only the
shipped bundle, the connection succeeds; with no trust anchors at all it is
refused — so the success comes from the bundle, not from an ambient default.

A standalone diagnostic (`QCS_diagnostico_update.ps1`) was written for the
field notebook: it separates DNS, port 443, proxy, the .NET call, the presence
of the required root and firewall rules, and prints a verdict.

# QCS v11.1 — Derived-variable flags, a structured phase verdict, a visible reset

> **MINOR** release (v11.0 → v11.1). **No QC result changes**: requalifying the
> same raw file under v11.1 produces the same flags — verified on real corpus
> inputs, column by column. The additions are two new output columns, one new
> structured verdict (warning only), one dialog and log hygiene.
>
> Every item in this release comes from a measured incident of the August 2026
> corpus rounds, not from speculation; the incidents are cited below.

## 1. Derived-variable flags: `Flag_dens` and `Flag_depth` (TSCP layout)

Density and Depth are COMPUTED columns — density from temperature and salinity,
depth from pressure — yet they carried no flag at all. The corpus sweep of
2026-08-11 showed why that matters: two RRDM03 moorings spent **90% of their
deployment at ~996 kg/m³** (fresh-water density — the conductivity read zero)
and the verdict lived only in `Flag_S`/`Flag_C`; anyone reading the Density
column at face value got no warning.

- `Flag_dens` = the worst of `Flag_T` and `Flag_S`, row by row (the
  density-inversion test already implicates exactly that pair in
  `FLAG_BUCKET_MAP`); `Flag_depth` = `Flag_P`. Severity order is the rollup's
  own: bad > suspect > missing > good > not evaluated.
- Purely additive: no existing flag changes. The columns sit after `Flag_lux`,
  before `QCS version`, in the TSCP layout only — HOBO files have no Density or
  Depth and their layout is byte-identical to v11.0.
- `PARAM_FLAG_COLUMN` maps `Density (kg/m3)` and `Depth (m)` to the new
  columns, so the DataView scale defaults now filter density/depth by approved
  rows like every other variable. Old databases (without the columns) fall
  back to the previous behaviour — the consumer already guarded for absence.
- `build_database` stacks old-layout and new-layout files without complaint
  (old rows carry NaN in the new columns, never an invented flag).
- The stale comment above `PARAM_FLAG_COLUMN` claiming CO2 has no flag column
  (false since v6.0) is fixed.

## 2. The light clock check has a third verdict: `anomalous` (structured)

`light_clock_phase` named two failures — the ±12 h antiphase and the collapsed
12-hour export — and the middle ground existed only as free-text ("worth a
look"), which nothing downstream could read. The field case that exposed it: a
logger whose light peaked at **4.4 h while its temperature peaked at noon** —
clock right, light channel wrong — sailed through every structured check and
its product shipped with 337 of 366 rows flagged GOOD from a failed sensor.
The lesson, verbatim from the corpus log: *a guard that keys on a specific
diagnosis does not cover a logger broken in a different way.*

- New key `anomalous: True` when the phase is ≥ 4 h off noon but below the
  accusation threshold: shading, heavy fouling or a faulty light channel.
- **Warning only.** It prescribes no shift and flags no data — the corpus
  light window is the fixed 60 days, so the phase drives no QC decision. The
  batch provenance now records it (`clock : ... ANOMALOUS PHASE`), so it can
  never again be invisible in a shipped product.
- Verified on the real corpus: the ESQRODO_B1 logger (light peaks 16.8 h
  across three independent exports — real shading, deliberately kept) comes
  out `anomalous`, with flags identical to its corpus product; a healthy
  logger (peak 11.7 h) does not.

## 3. The version-gated settings reset is now visible

Since v3.2 a version change resets saved QC criteria to the new defaults on
purpose — but the only trace was one log line, easy to miss (the batch logs
showed machines still carrying v8.0-era settings). On the first launch after a
version change the app now says so in a dialog: criteria reset to the new
defaults, folders and preferences kept, where to re-tune.

The dialog lives in `QCS_App` (the GUI shell), NOT in the settings loader: the
headless and batch paths drive `QCS_Main` directly and never import the shell,
so they can never block on it. Verified: the batch harness under v11.1 prints
the log line and no dialog.

## 4. Once-per-run warning dedup

The spike/rate-of-change window warnings fire per test call, and one
qualification runs the same test over up to nine variables — the same line
landed in the Execution log up to nine times per file. Identical warnings are
now printed once per qualification run (`reset_run_warnings` clears the memory
at RUN start).

## Outside the app (no version impact)

The batch lane gained, in the same change set: `build_data_package.py` (the
site/period delivery bundle, promoted from the August one-off, English output,
zip fallback when WinRAR is absent); `drop_stale_products.py` now MOVES removed
products into `CLAUDE\_deleted\<date>\` instead of deleting (the share has no
recycle bin); `build_index.py` ends every corpus round by running
`sweep_value_integrity.py` and fails loudly if the sweep does; the sweep's
output is now English.

## Verification

48 self-tests pass (three new: derived flags incl. old+new file stacking,
anomalous verdict, warning dedup), ruff clean. Real-data check without touching
the corpus: RH3 2019S2 Seaguard mooring requalified into a tempdir — 97 rows,
**every pre-existing column identical** to the corpus product, the new columns
obeying their definition on every row; ESQRODO_B1 and a healthy HOBO likewise
flag-identical with the expected verdicts.

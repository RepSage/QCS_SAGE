1. Introduction

QCS (Quality Control System) is a complete solution for the qualification and visualization of oceanographic data from two instrument families: Seaguard/TSCP (temperature, salinity, conductivity, pressure, O₂, pH, chlorophyll, turbidity — profiles and moorings) and, since v4.0, HOBO Pendant (temperature and light — see section 9). This manual covers every aspect of the system, from installation to advanced operations.

2. Installation

Minimum Requirements

  • Windows 10 or later (64-bit)
  • Python (Anaconda is recommended) with the packages from sourceCode/requirements.txt: numpy, pandas, matplotlib, scipy, openpyxl and gsw
  • sv-ttk (optional, included in requirements.txt): the "Sun Valley" visual theme (Windows 11 look, with light/dark mode). Without it, the interface uses the classic look — nothing stops working.

New in v4.0: a modernized interface with a dark mode (toggle in the window header, preference remembered across sessions), crisp text on high-resolution displays, and an "Execution log" panel in the main windows that shows the progress, warnings and errors of each run, color-coded by severity.

Basic Installation

QCS runs directly from the Python scripts (there are no more executables). To set it up:

  1. Obtain the project folder (containing the sourceCode subfolder and the .bat shortcuts)
  2. Install the dependencies by running in the terminal: 
    python -m pip install -r sourceCode/requirements.txt
  3. Open QCS.bat

Since v5.0, both tools live in a single window (open with QCS.bat): a menu bar (File / Edit / View / Tools / Help) plus two tabs, Data Qualification and Data Visualization. Dark mode is under the View menu.

Since v4.0, the app runs with no terminal window (launched via pythonw): all progress, warnings and errors appear in the Execution log. Since v5.0 this is one single panel, fixed at the bottom of the window — the same log, in the same place and with the same message styling, for every pipeline stage (qualification, database building/preview and panel generation). If a fatal error happens before the window can open, a message box appears and a sourceCode/QCS_crash.log file is written with the details.

5. Qualification Flags

Flag Structure

Each data point receives a flag string in the format [TEST1][TEST2]...[TESTN], where each test is represented by a digit:

Code Meaning Description
1 GOOD_DATA Data passed the test
2 UNKNOWN Test could not be applied (insufficient data)
3 SUSPECT Suspect data (failed by a margin)
4 BAD_DATA Data failed the test
5 DISMISSED Point dismissed by the operator (manual point cut), or the test was disabled
9 MISSING Missing data/NaN

Flag Construction

  • Tests are applied sequentially
  • Each test appends its code to the end of the flag string
  • The test order is fixed (sensor range → environmental range → spikes → rate of change → flat line → vertical gradient and density inversion, these two for profiles only → light usable window, HOBO only)
  • Flags are cumulative - a data point can have multiple codes
  • The exact position → test → variable mapping is written to the QCS_flag_legend.xlsx file, generated with each qualification (v4.0)

Example

The flag 1942 means:

  • 1: Passed the first test (sensor range)
  • 9: Missing data in the second test
  • 4: Failed the third test
  • 2: Test not applied in the fourth test

Per-variable Flag_ columns (v4.0)

Besides the full Flag string, the qualified file carries a summary column per variable (Flag_T, Flag_S, Flag_C, ..., Flag_lux in HOBO files), with the worst flag of that variable in that row (priority 4 > 3 > 9 > 1 > 2 > 5). This way you do not need to decode the string position by position to filter data by quality — for example, keeping only the rows with Flag_T <= 2 in a temperature analysis.

6. Settings Management

All quality criteria (tests on/off, parameters and per-variable factors) are adjusted in the Settings window, opened by the Settings button in the main window. The choices are saved automatically across sessions.

Change in v4.0: the old Export Settings (export .json) and Config File (import .json) were removed from the interface — configuration is now done entirely in the Settings window. Preferences are still saved automatically in the qcs_user_settings.json file (generated by the program, not versioned).

Reset to defaults

The Settings window has a "Reset to Defaults" button that returns all criteria to the defaults of the installed version. Invalid values typed in the fields are listed in a warning, instead of being silently ignored.

Note when upgrading from older versions: because of the version control of the preferences, the first time you run v4.0 the quality criteria saved from v3.2.1 are replaced by the current defaults (intentional behavior — the criteria were revised). File paths and last choices are preserved.

        "salinity sensor range": "ON",
        ...
    },
    "tsSettings": {
        "sensor_min_temp": -5,
        "sensor_max_temp": 35,
        ...
    }
}

7. Detailed Configuration Parameters

Note (v3.1): time_window, fail_factor and susp_factor are now defined per variable, in the "Factors per Variable" tab of the Settings window (one row per variable, columns Fail / Susp / Time window). The descriptions below apply to each variable.

time_window

Defines the time window for standard-deviation calculations in the spike and rate-of-change tests.

Accepted formats:

  • "WHOLE": Uses the whole dataset
  • "Xd": X days (e.g. "7d")
  • "Xh": X hours (e.g. "24h")
  • "Xm": X minutes (e.g. "30m")
  • "Xs": X seconds (e.g. "300s")

Effects:

  • Smaller windows are more sensitive to local variations
  • Larger windows smooth variations but may mask anomalies
  • For long mooring data, 1h-12h is recommended (depending on the sampling interval)
  • For profiles, 1m-6m is usually adequate

fail_factor and susp_factor

Deviation multipliers for classifying data. Since v4.0, the reference for the spike and rate-of-change tests is a robust deviation (1.4826 × MAD, the median absolute deviation): the spurious value itself no longer inflates the threshold that should detect it. Where the MAD degenerates (near-constant series), the calculation falls back to the ordinary standard deviation.

Behavior:

  • fail_factor > susp_factor (typically 3 and 2.5)
  • High values reduce false positives but may let errors through
  • Low values increase sensitivity but also false positives
  • For noisy data, increase both by 0.5-1.0
  • For very stable data, you can reduce by 0.5

HOBO light-window parameters (lux_*)

In the Parameters tab of the Settings window, the parameters with the lux_ prefix control the light fouling test (HOBO only — see section 8):

  • lux_baseline_days: how many initial days define the clean-water baseline (the highest daily light peak in that period)
  • lux_cutoff_frac: the fraction of the baseline below which the daily peak indicates fouling
  • lux_sustain_days: for how many consecutive days the peak must stay below the threshold to confirm the cutoff

The values used are written on the QCS_light_window.svg plot itself, in the log and in QCS_test_report.xlsx — the cutoff is always traceable.

How to Access Help

  • Tooltips: Hover over any interface element to see a hint
  • Help button (?): In the header of each window; it includes the basic instructions and the information about the software (the old menu bar was removed in v4.0)

8. Qualification Tests

Processing Flow

  1. Pre-processing (unit corrections, GMT-3)
  2. Range Tests (sensor and environmental)
  3. Spike Tests
  4. Rate-of-Change Tests
  5. Flat Line Tests
  6. (For profiles) Vertical Gradient and Density Inversion Tests
  7. (For HOBO) Light usable window (fouling)
  8. Output generation

The log announces the pipeline in 5 stages (reading → pre-processing → tests → output/reports → plots), which makes it easier to find where a run failed.

Sequential Order of the Qualification Tests (v4.0)

  1. Sensor Range Tests — failure becomes BAD (4) (physically impossible value for the sensor)
    • Temperature, Salinity, Conductivity, Pressure, Dissolved Oxygen, pH, Chlorophyll, Turbidity
  2. Environmental Range Tests — failure becomes SUSPECT (3) (QARTOD alignment: outside the regional envelope is suspect, since a real extreme event is possible)
    • Temperature, Salinity, Conductivity, Pressure, pH, Chlorophyll, Dissolved Oxygen, Dissolved Organic Matter, Turbidity
  3. Spike Tests (Spurious Values) — 3-point method
    • Temperature, Salinity, Conductivity, Pressure, pH, Chlorophyll, Dissolved Oxygen, Dissolved Organic Matter, Turbidity
  4. Rate-of-Change Tests — failure becomes at most SUSPECT (3) (QARTOD: real rapid variation exists)
    • Temperature, Salinity, Conductivity, Pressure
  5. Flat Line Tests
    • Temperature, Salinity, Conductivity, Pressure
  6. Vertical Gradient Tests (Profile data only) — real |ΔV/Δz| relative to the profile's typical gradient
    • Temperature, Salinity, Conductivity
  7. Density Inversion Test (Profile data only)
    • Checks water-column stability: the potential density (computed from T, S and pressure) must not decrease with depth beyond a tolerance (configurable in Settings; default 0.03 kg/m³). An inversion indicates a suspect temperature/salinity pair (flag 3) and implicates both — it is not force-dropped; it only leaves the result if "Remove Suspect Data" is on.
  8. Light usable window (HOBO only)
    • Light fouling (biofouling) test — see the HOBO Data section. It generates the light flag position (Flag_lux).

HOBO files: since the HOBO Pendant measures only temperature and light, only the temperature tests from the list above are run, plus the light window test. The flag string stays short and free of meaningless positions.

Note (v3.0): the qualification criteria were revised in this version to be broad and general (valid for the entire Brazilian coast, from the South to the Amazonian reefs). The spike test switched to the 3-point method (|V₂ − (V₁+V₃)/2|), and the density inversion test was added for profiles. Because it changes the qualification results relative to the 2.x versions, it is a major version (v3.0).

Note (v4.0): a new revision that changes results relative to v3.x: the environmental range and rate of change now produce SUSPECT (not BAD), per QARTOD; the spike/rate-of-change reference is now the robust deviation (1.4826×MAD); the vertical gradient now actually uses depth (|ΔV/Δz|); and several bug fixes (detailed in the project's changelog/v4.0.md file). With "Remove Bad Data", values outside the environmental envelope are no longer removed automatically — use "Remove Suspect Data" for the old behavior.

Test Details

Each test produces detailed logs in the console, including:

  • Execution time
  • Number of failed data points
  • Failure percentage

Section: Joining Files in QCS_DatabaseView (build_database engine — v4.0)

Two ways to build the database

In the Database Input Settings window, first choose the Instrument (Seaguard or HOBO — the two are never mixed in the same database) and then:

  1. Manual selection: in "Database File(s)", select one or several qualified files (.csv or .xlsx, in any combination) — they are combined, validated and deduplicated automatically; or
  2. Build database from a folder (parent folder): check the option and point "Input Path" to the folder that contains the QCS outputs. The scan is recursive: any subfolder named exactly QCS qualified tscp data (Seaguard) or QCS qualified hobo data (HOBO) is found, at any level.

Folder structure (example for Join mode)

All_Data/
├── Camp1/
│   └── QCS qualified tscp data/
│       └── data_camp1.csv
├── Camp2/
│   └── QCS qualified tscp data/
│       └── data_camp2.xlsx
└── Camp3/
    └── QCS qualified tscp data/
        └── data_camp3.csv

What the unification engine does

  • Validates the layout of each file (requires the Datetime and Site columns) and detects whether it is Seaguard or HOBO — mixing types is refused with a clear message.
  • Ignores the report files (anything starting with QCS_: report, stat, flag legend, etc.) — only data enters the database.
  • Discards exact duplicates (same site, timestamp and values), keeping the first occurrence and warning in the log; overlaps with different values (same site+timestamp from distinct files) are kept and reported with the list of files involved, for the operator to decide.
  • Adds a Source file column (which file each row came from — provenance) and sorts by Site + Datetime.
  • Shows a per-site summary in the visualization window log (number of rows and period covered).

If "Build database from a folder" is checked, the unified database is also saved as .xlsx (with the name from the "Output Name" field) in the DatabaseView folder inside the Output Path, for reuse.

9. HOBO Data (Temperature and Light)

Since v4.0, QCS qualifies and visualizes data from the HOBO Pendant (Temperature/Light) loggers, in addition to Seaguard. Select Input Type = HOBO in the main window and point to the HOBOware export.

Reading the files

  • Accepts the .xlsx and .csv HOBOware exports, with headers in Portuguese or English (the header row and the delimiter are detected automatically; broken accents are tolerated).
  • Automatic light unit: lux is used directly; lum/ft² (foot-candle) is converted to lux (×10.7639). The output is always in lux.
  • Deployment window from the logger events (Coupler On/Off, Stopped, End of File): rows outside the in-water period and event-only rows are discarded, with a note in the log. Out-of-water readings at the edges are also trimmed by a temperature jump (parameter hobo_edge_temp_tol, with a safeguard against removing more than 10% of the series).
  • Zero light at night is a valid value (never becomes missing); negatives become 0.

Qualification

The temperature tests applicable to a mooring are run (sensor and environmental range, spike, rate of change and flat line — producing Flag_T) plus the HOBO-exclusive test:

Light usable window (fouling test)

With the sensor at sea, fouling organisms gradually cover the logger and the measured light decays — beyond a certain point, it is no longer reliable. The test identifies that point:

  1. The clean-sensor baseline is the highest daily light peak of the first lux_baseline_days days (the max, so a cloudy install day does not lower it);
  2. From the start of the final sustained decline — where the daily peak stays below lux_cutoff_frac × baseline for at least lux_sustain_days consecutive days and never recovers to the threshold — the light is flagged BAD (4, unusable). Light that recovers above the threshold is kept. The values stay in the sheet until you remove them with "Remove Bad Data";
  3. If, after the cutoff, the light still reaches the threshold on a good share of the days (~20%+), a warning indicates that the decline is not permanent (possible sensor cleaning, multiple deployments in the same file, or a cloudy period) — review it.

Interactive review: before applying, the program shows the daily light envelope with the proposed cutoff — a click moves the cutoff date, the N key removes the cutoff, Enter/close confirms. The final plot is saved as QCS_light_window.svg in the output folder, with the parameters used written on it.

Limitation: the test identifies one cutoff per file. If the sensor was cleaned and returned to the water in the same file, the recovery warning will fire — it is recommended to qualify each deployment (between cleanings) as a separate file.

Output

The qualified HOBO spreadsheet contains only the measured variables + metadata: Sample number, Datetime, Temperature (degC), Luminosity (lux), Expedition, Site, Battery voltage (V), Flag, Flag_T, Flag_lux, QCS version. It is saved in the QCS qualified hobo data subfolder (the Seaguard one remains QCS qualified tscp data). HOBO and Seaguard spreadsheets are never combined in the same database.

To visualize HOBO databases (dedicated temperature and light panels with the fouling window shaded), see section 11.

Redundant replicates (2-4 HOBOs)

When two or more HOBOs are deployed together for redundancy, simply select all the files at once with Browse — the Replicates box shows how many were picked (the count is program-determined, no manual choice). Each replicate is qualified independently (its own light-window review) and then combined into a single series, saved to a <site>_<start>_<end>_combined_QLF folder (the individual per-file _QLF outputs are also kept). The method is written to QCS_combine_method.txt in the combined folder, and each replicate's QCS_light_window_<replicate>.svg is copied there.

  • Temperature: the mean of the replicates that are acceptable (Flag_T ≤ 2) at each timestamp. Replicates are aligned to the first replicate's timestamps by nearest match within half the sampling interval (redundant HOBOs are never started at the exact same second, but that offset is tiny versus the sampling step, so paired readings are effectively simultaneous — it is a nearest match, not interpolation). The between-replicate spread (max − min) is kept in the Temperature spread (degC) column; when it exceeds 0.5 °C the combined Flag_T is set to SUSPECT (3) — the replicates disagree, which is itself a QC signal.
  • Light: the per-timestamp maximum of the non-fouled readings (Flag_lux ≠ 4). Fouling only attenuates light, so the brightest unfouled sensor is the most reliable. The combined light stays good while at least one replicate is unfouled and becomes BAD (4) only once every replicate is fouled — the usable window is extended to the last replicate to foul. Light is not averaged (that would mix clean and fouled sensors).

File Contents

  • Qualified File:
    • All the raw data (except what "Remove Bad/Suspect Data" removes)
    • A "Flag" column (full string) and Flag_T, Flag_S, ... columns per variable (worst flag of the row — v4.0)
    • Metadata (site, QCS version). Latitude/Longitude are not written (identical column layout across spreadsheets)
  • Report (QCS_report.xlsx):
    • Bad/suspect/missing counts for the 9 variables
    • Timestamp checks (backward steps, duplicates, large gaps)
    • "Valid" discounts rows with bad data in any variable
  • Per-test report (QCS_test_report.xlsx — v4.0):
    • One row per executed test: good/suspect/bad/missing counts, test off, and execution time
  • Flag legend (QCS_flag_legend.xlsx — v4.0):
    • Two sheets: flag_positions (flag-string position → test → variable) and flag_codes (the meaning of each code)
  • Statistics (QCS_tscp_stat.xlsx):
    • Mean, median, standard deviation
    • Minimum and maximum values
    • Valid-data count (all variables present)
  • Light window (QCS_light_window.svg — HOBO only, v4.0):
    • Daily light envelope with the baseline, threshold and fouling cutoff applied, and the parameters used written on the plot

Scale Configuration

Advanced control over the plot scales through the "SCALE SETTINGS" panel.

Fixed vs. Automatic Scales

Type Description When to Use
Fixed Scale Lets you set manual minimum and maximum values for each parameter
  • Direct comparison between different datasets
  • Keeping visual consistency between plots
  • Highlighting specific variations in known ranges
Automatic Scale The system adjusts automatically to show all the data
  • Initial exploratory analysis
  • When the data amplitude varies significantly
  • To view the full data distribution

How to Configure Fixed Scales

  1. Check the "Fixed Scale" option in the visualization section
  2. Select the desired parameters in the "Select Parameters" section
  3. For each selected parameter:
    • Type the minimum value in the corresponding field in the "Min Value" column
    • Type the maximum value in the corresponding field in the "Max Value" column
  4. Save the settings with "Save View Settings"

Tip: The scale fields are only enabled when:

  1. The "Fixed Scale" option is checked
  2. The corresponding parameter is selected
  3. At least one visualization panel is active

Filters and Data Selection

The system offers multiple options to focus on specific subsets of the data:

Time Filter

  • By Year: Type a specific year in the "Filter by Year" field
  • By Date/Time: Use the chronological sorting ("Sort by Time" in the input window)

Spatial Filter

  • Select specific sites in the "Filter by Site" list
  • For profiles, the coordinates can be used in the T-S Diagram

Parameter Selection

  • Enable/disable parameters individually as the analysis requires
  • Combine relevant parameters for multivariate analysis

Advanced Visualization Options

Option Description Application
Trend Lines Adds polynomial trend lines Identify temporal patterns
Show Data Points Shows individual points in addition to the line Visualize data density
Fixed Scale Keeps consistent scales between plots Quantitative comparison

Warning: Poorly configured fixed scales can:

  • Hide important variations if the range is too wide
  • Cut off valid data if the range is too narrow
  • Distort the visualization if the min/max are inverted
Always check the raw data before setting fixed scales.

Recommended Workflow

  1. Start with automatic-scale visualizations for initial exploration
  2. Identify typical ranges for each parameter
  3. Apply filters to focus on the relevant data
  4. Configure fixed scales for systematic comparisons
  5. Use trend lines to identify patterns
  6. Save useful settings for reuse

13. Running from Source Code

Since version 2.2, QCS runs directly from the Python scripts — there are no more executable (.exe) builds. This means any fix in the scripts takes effect immediately, with no need to recompile.

Requirements

  • Python (Anaconda is recommended)
  • The project dependencies installed (see section 2): numpy, pandas, matplotlib, scipy, openpyxl, gsw (and optionally sv-ttk for the modern theme)

How to run

The recommended way is via the QCS.bat shortcut in the main folder, which already calls the correct Python and opens the unified app. Alternatively, in the sourceCode folder, you can run the scripts directly:

python QCS_App.py           # unified app (both tabs) - the normal entry point
python QCS_Main.py          # qualification tool only (development)
python QCS_DatabaseView.py  # visualization tool only (development)

Quick check (self-tests)

To confirm the qualification functions are intact after a change, run in the sourceCode folder:

python QCS_SelfTest.py

14. Troubleshooting

Common Problems and Solutions

Problem Solution
File does not load Check the format and encoding (use UTF-8)
Tests not applied Check that the parameter name matches what is expected
Plots not generated Check that the data has valid values
Memory error Reduce the dataset size or add memory
The program does not open / closes with a message box A fatal error occurred before the window could open. Read the message box, and check sourceCode/QCS_crash.log for the full details
"No year selected" when generating panels Check at least one year in "Filter by Year" and click "Save View Settings" again
"build_database: ..." when building the database The message points to the file and the exact problem (missing column, mixing of Seaguard/HOBO layouts, etc.). Check that the selected Instrument matches the files and that all of them are qualified QCS outputs
T-S diagram skipped Fill in Latitude and Longitude with valid values (decimal degrees) — they are required for the T-S
Light recovery warning after the cutoff (HOBO) The file may contain more than one deployment (sensor cleaned and returned to the water); review the cutoff in the interactive window or qualify each deployment separately

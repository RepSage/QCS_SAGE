1. Introduction

QCS (Quality Control System) is a complete solution for the qualification and visualization of oceanographic data from two instrument families: Seaguard/TSCP (temperature, salinity, conductivity, pressure, O₂, pH, chlorophyll, turbidity — profiles and moorings) and HOBO Pendant (temperature and light — see section 9). This manual covers every aspect of the system, from installation to advanced operations.

2. Installation

Minimum Requirements

  • Windows 10 or later (64-bit)
  • Nothing else for the installed program — the installer is self-contained (no Python and no libraries to install). Running from source instead requires Python and the project dependencies (see section 14).

Installing (recommended)

  1. Download QCS_Setup_v<version>.exe from the project's releases page and run it.
  2. Choose the installation mode: install for all users (goes to C:\Program Files\QCS, asks for an administrator account) or install for me only (user area, no administrator needed — the right choice for a field notebook).
  3. Open QCS from the Start Menu or the Desktop shortcut.

Two first-run notes: Windows SmartScreen may warn about an unrecognized publisher (the installer carries no code-signing certificate) — choose "More info → Run anyway". And the very first launch takes ~15–20 s while the plotting library builds its font cache, one time only; after that the program opens in a few seconds.

The interface at a glance

The three workflows live in a single window (Qt, Fusion style): a menu bar plus the Data Qualification, Curated Database and Data Visualization tabs. File carries the file-level actions of the tab (select data file(s), Ctrl+O; add CO₂ data; select or open the output folder; quality control settings; exit, Ctrl+Q), View the dark and Field modes and the Execution log / Batch status panels, and Help the user manual, Check for updates and About. Bugs & Suggestions, beside Help, opens an internal form that submits a report directly to the project; no account on the project website is required. The interface offers a dark mode and a Field mode (both in the View menu and remembered across sessions). Field mode disables only the Curated Database tab, preventing accidental corpus work during field collection; turn it off to restore the tab. Hovering the menu action or disabled tab explains the restriction. Text remains crisp on high-resolution displays. The Run qualification button enables only when everything required is filled — the hint under it names the next missing step — and a progress bar (bottom right) follows the pipeline stages, prefixed with the batch/replicate scope (e.g. Replicate 2/2 - Stage 3/5). While a qualification or curated-database job is running, all three workflow tabs are dimmed; the active page remains visible so its Cancel button stays available.

The app runs with no terminal window: all progress, warnings and errors appear in the Execution log — one single panel at the bottom of the window, the same log for every pipeline stage (qualification, database building/preview, panel generation and curated-corpus export), color-coded by severity. The log is a dockable panel: drag it, detach it into its own window, or close it — View > Execution log brings it back; messages keep accumulating while hidden. During a batch a Batch status panel lists one row per file with its state (running / ok / FAILED), and when a run finishes two shortcuts appear under the RUN button: Open output folder and Go to visualization.

The left side of the status bar states which quality criteria are in force: criteria: defaults or criteria: CUSTOM. In the Quality control settings window every field that differs from the software default is shown in bold, each row carries a circular-arrow button that restores just that parameter, and a Find box filters the rows by name — so it is always visible whether a qualification ran with the canonical criteria or with edited ones. The Bold = differs from defaults key is itself bold so the convention is not hidden in a tooltip. If a fatal error happens before the window can open, a message box appears and a QCS_crash.log file is written with the details — next to QCS.exe on an installed copy (in %APPDATA%\QCS for a Program Files install), or in sourceCode/ when running from source.

INPUT SETTINGS Section

The Input settings and Output settings cards keep the same equal-width split when the selected instrument shows or hides optional controls. Editable text fields provide a trailing × inside the field whenever they contain text; it clears the value without requiring it to be selected first, uses the pointing-hand cursor and fades smoothly in or out as text appears or disappears. Raw .hobo files (HOBO Pendant Temp/Light) can be qualified directly, without exporting from HOBOware (experimental): the binary is decoded with calibration tables derived from and validated against this archive's 200+ file/export pairs; temperature and light reproduce the HOBOware export exactly on the current-generation files. The reading HOBOware shows at launch (taken in air during configuration) is not stored in the binary, so the series starts one interval after launch. A file from an older HOBOware generation that does not fit the deciphered layout is refused with a clear message — qualify those from their exported sheets.

Data type Dropdown with the collection type: TSCP Profile, TSCP Mooring or TSCP Doppler (the last one is set automatically when a current-profiler session is selected). It does not apply to HOBO — a pendant logger is always a time series — and the field says that itself while it is greyed out.

Set automatically for a Seaguard raw session (v13.0). A cast is lowered and recovered in minutes and logged fast; a mooring is left down for hours to weeks and logged slowly. When a .bin is selected the program times the session and detects TSCP Mooring or TSCP Profile, writing what it found in the log and in the Selection summary. A conclusive detection locks the field, including after a file is cleared and dropped again. If there are too few timestamps to decide, or the session is both short and logged at a slow mooring cadence (a pattern that occurs as both types in the labelled archive), the field remains editable and the log asks you to check it. A DCPS session is identified directly from its binary layout and is locked on TSCP Doppler.

Select profile data Checkbox (enabled only for profiles) to select the downcast/upcast phase.
Check variables Opens a manual point-cut panel per variable; you first pick which variables to review (with "All variables" / "None"). Each panel lets you drag a box to dismiss points (mouse-wheel zoom; Undo / Reset / Skip / Done / Help; live counter and an "X of N" progress). The selection box keeps following the mouse when it leaves the plot, clipped to the axes, so points sitting on an edge can be enclosed without fighting the border; it disappears as soon as the selection is applied, leaving a clean view for the next box. Current profiler (DCPS). A current session has its own review. The tilt panel always runs, one point per record — it is the DCPS's equivalent of the Depth review, and cutting a point dismisses the whole record, every depth cell of that instant (the cut cannot be made on depth: in a current table Depth (m) is the CELL depth). With Check variables ticked, the chooser then offers the variables a current table actually carries: horizontal speed, direction, vertical speed, speed stdev and signal strength, each shown one depth cell at a time, in sequence. A dismissal there condemns the whole cell sample — speed, direction and the U/V/W components of a cell are one velocity solution — so every flag position of the row becomes 5 and every measurement is blanked, the row keeping its Datetime, Site, Column, Cell and Depth. Macroregion / Region Two cascading dropdowns. Macroregion is the broad region (currently only Brazil, structured to add other parts of the world in the future) and Region is the sector within it — for Brazil: Amazonian Reefs/North, Northeast–northern, Northeast–eastern, East/Abrolhos, Southeast, South. Each region defines a representative latitude/longitude, used only to run the qualification (pressure-to-depth conversion and the density inversion test). Small coordinate variations do not affect these calculations, so picking a region is enough and simpler than typing values. The coordinates are not written to the qualified spreadsheet. Not applicable to HOBO (no pressure).

5. Qualification Flags

Flag Structure

Each data point receives a flag string in the format [TEST1][TEST2]...[TESTN], where each test is represented by a digit:

Code Meaning Description
1 GOOD_DATA Data passed the test
2 UNKNOWN Test could not be applied (insufficient data)
3 SUSPECT Suspect data (failed by a margin)
4 BAD_DATA Data failed the test
5 DISMISSED Point dismissed by the operator (manual point cut), or the test was disabled
9 MISSING Missing data/NaN

Flag Construction

  • Tests are applied sequentially
  • Each test appends its code to the end of the flag string
  • The test order is fixed (sensor range → environmental range → spikes → rate of change → flat line → vertical gradient and density inversion, these two for profiles only → light usable window, HOBO only)
  • Flags are cumulative - a data point can have multiple codes
  • The exact position → test → variable mapping is written to the QCS_flag_legend.xlsx file, generated with each qualification
  • A current profiler (DCPS) sheet has its own five-position string, listed in QCS_current_flag_legend.txt beside the qualified table: speed range, signal quality, speed stdev, instrument tilt and the operator's manual review (2 = no review ran, 1 = reviewed and kept, 5 = dismissed). A current table qualified before v13.0 carries four positions and has to be requalified to gain the fifth

Doppler quality-control settings do exist. The Quality control tests tab lists four independent automatic switches under Seaguard current profiler (Doppler); the Parameters tab contains their five numeric thresholds. By default, speed above 300 cm/s is BAD; a nonzero instrument cell state, signal below −60 dB or the no-ping 0 dB value is BAD; speed standard deviation above 50 cm/s is SUSPECT; and tilt above 15°/35° is respectively SUSPECT/BAD. Missing speed produces a missing flag. The fifth flag position records whether manual review ran and whether the operator dismissed that complete cell sample. Flag_cur is the row's worst result. These criteria are independent of the visualization settings.

Example

The flag 1942 means:

  • 1: Passed the first test (sensor range)
  • 9: Missing data in the second test
  • 4: Failed the third test
  • 2: Test not applied in the fourth test

Per-variable Flag_ columns

Besides the full Flag string, the qualified file carries a summary column per variable (Flag_T, Flag_S, Flag_C, ..., Flag_PAR in Seaguard files and Flag_lux in HOBO files), with the worst flag of that variable in that row (priority 4 > 3 > 9 > 1 > 2 > 5). This way you do not need to decode the string position by position to filter data by quality — for example, keeping only the rows with Flag_T <= 2 in a temperature analysis.

Derived-variable flags: Flag_dens and Flag_depth

Density and Depth are computed columns — density from temperature and salinity, depth from pressure — so they carry a derived flag rather than none: Flag_dens is the worst of Flag_T and Flag_S in the row, and Flag_depth equals Flag_P. A density read from a dead conductivity cell (~996 kg/m³, fresh-water density) therefore announces itself instead of looking like data. TSCP layout only; HOBO files have neither column. Files qualified by older program versions may lack the two columns — merging old and new files in the database builder works, with the old rows left empty there.

PAR qualification

A Seaguard PAR (umol/m2/s) channel is read, merged, qualified and available in Data Visualization as PAR (µmol/m²/s). It follows the same optical-sensor sequence as chlorophyll and turbidity: sensor range (0–5,000, outside = BAD), environmental range (0–4,000, outside = SUSPECT), and the configurable robust spike test. These three results roll up to Flag_PAR. For the spike calculation, valid night zeros are excluded from the robust scale so a zero-heavy night cannot make a smooth daylight curve look like mass spikes; a stable run of night zeros passes. Rate-of-change, flat-line and vertical-gradient tests do not apply to PAR.

Negative dark-offset readings are still clamped to zero before the tests; zero is a valid night reading. Archived templates identify both PAR-SER ICSW #1372 and Satlantic PAR #2301 with a 0–5,000 µmol/m²/s range. Across the 123 archived qualified products containing PAR, 311 of 158,815 finite values (0.20%) exceed 4,000 and none exceeds 5,000, which keeps rare high observations visible as SUSPECT while reserving BAD for values outside the sensor range. A read-only replay of all three tests rolled those finite values up as 156,293 GOOD, 1,099 SUSPECT and 1,423 BAD, with no read error; the remaining 19,142 rows had missing PAR. Products qualified before v13.0 do not contain Flag_PAR; requalify their raw data before comparing qualification results. HOBO lux is a separate relative visible-light measurement and is not a substitute for PAR.

Light clock check: the anomalous-phase verdict

For HOBO files, the light clock check names three situations rather than two: a clean ±12 h antiphase (AM/PM swapped at launch), the collapsed 12-hour export (no AM/PM marker at all), and now an anomalous phase — the light peaks well off noon but no clock error explains it, which points at shading, heavy fouling or a faulty light channel. The verdict is a warning in the Execution log and in the batch provenance; it prescribes no correction and flags no data (the corpus light window is the fixed 60-day rule, so the phase drives no QC decision).

6. Settings Management

All quality criteria (tests on/off, parameters and statistical thresholds) are adjusted in the Quality control settings window, opened by the button of that name or from File → Quality control settings…. The choices are saved automatically across sessions.

Every tab uses the same instrument order: Seaguard, Seaguard current profiler (Doppler), then HOBO. The tests are genuinely independent: disabling the HOBO temperature range, spike or rate-of-change test does not disable its Seaguard counterpart. Doppler has switches for speed range, signal quality, speed standard deviation and tilt. Manual point review is selected during qualification and therefore is not an automatic-test checkbox.

What the program remembers

Closing the program stores, and the next launch restores:

  • the window as it was left — size, position and maximized state — the height the Execution log was dragged to, and whether it was hidden;
  • the qualification form: files, output folder, name and format, site code, macroregion and region, and the option checkboxes. They are kept even if the run was never started;
  • the visualization choices: the database and output fields, the instrument, the panels and the plot colors set per parameter;
  • the recent selections of Qualification and Visualization, the Curated Database corpus/output folders and output name, the dark and Field modes, and the folders each Browse dialog should open at.

The quality criteria are the one exception, by design: see the note below.

The first launch after a program update shows the main window before displaying a dialog when your saved QC criteria were reset to the new version's defaults. The reset is deliberate — a version may change criteria on purpose, and keeping old saved values would silently mask that. Folders, file choices and visualization preferences are always kept, and custom criteria can be set again in the Settings window.

Updates

When the program starts it quietly checks GitHub for a newer release; with no internet connection nothing happens — the check never blocks or interrupts work. When a newer version exists, a dialog offers to download and install it: the program downloads the installer, closes itself and hands over to the installer's wizard. Its last page offers Launch QCS after installation, ticked by default — leave it ticked and the program comes back updated, with all settings kept. 7. Detailed Configuration Parameters

Across the three Quality control settings tabs, variable controls use the same display sequence as Data Visualization: Temperature, Salinity, O₂, pH, Chlorophyll, Turbidity, PAR, CO₂ and Organic matter first, followed by the available members of the rarely-used tail — Conductivity, Pressure, Density and Soundspeed. A variable is not given a placeholder control for a test that does not apply: Density has only its profile criterion and Soundspeed has no independent quality test.

The Statistical thresholds tab separates thresholds by instrument, test and variable. It shows only fields used by that algorithm: spike has Bad, Suspect and Time window; rate of change has Suspect and Time window; vertical gradient has Bad and Suspect. Each visible parameter name ends in a colon. HOBO temperature has its own spike and rate-of-change rows. A row is disabled when its corresponding test checkbox is off. Doppler uses direct physical limits in Parameters, so its section in this tab contains no statistical fields.

time_window

Defines the time window for standard-deviation calculations in the spike and rate-of-change tests.

Accepted formats:

  • "WHOLE": Uses the whole dataset
  • "Xd": X days (e.g. "7d")
  • "Xh": X hours (e.g. "24h")
  • "Xm": X minutes (e.g. "30m")
  • "Xs": X seconds (e.g. "300s")

Effects:

  • Smaller windows are more sensitive to local variations
  • Larger windows smooth variations but may mask anomalies
  • For long mooring data, 1h-12h is recommended (depending on the sampling interval)
  • For profiles, 1m-6m is usually adequate

fail_factor and susp_factor

Deviation multipliers for classifying data. The reference for the spike and rate-of-change tests is a robust deviation (1.4826 × MAD, the median absolute deviation): the spurious value itself does not inflate the threshold that should detect it. Where the MAD degenerates (near-constant series), the calculation falls back to the ordinary standard deviation.

Behavior:

  • For spike and vertical gradient, fail_factor > susp_factor (typically 3 and 2.5); rate of change has only a suspect factor
  • High values reduce false positives but may let errors through
  • Low values increase sensitivity but also false positives
  • For noisy data, increase both by 0.5-1.0
  • For very stable data, you can reduce by 0.5

Parameters tab organization

Instrument capabilities are kept separate: Seaguard sensor limits cannot silently change HOBO limits. The tab is ordered as Seaguard sensor/profile settings, Seaguard current profiler thresholds, HOBO temperature/deployment settings, Light plots, Light fouling, and finally the shared environmental ranges. The former ambiguous Other parameters section no longer exists.

Flat-line thresholds are still expressed in samples. The test treats changes up to the decimal resolution inferred from the series as effectively identical; missing samples do not break a run. For that reason Pressure flat line remains OFF by default: a fixed instrument can legitimately repeat quantized pressure values. A future duration-based criterion requires corpus validation before it can safely become a default.

HOBO light-window parameters (lux_*)

In the Parameters tab of the Settings window, the parameters with the lux_ prefix control the light fouling test (HOBO only — see section 8):

  • lux_baseline_days: how many initial days define the clean-water baseline (the highest daily light peak in that period)
  • lux_cutoff_frac: the fraction of the baseline below which the daily peak indicates fouling
  • lux_sustain_days: the minimum length of the final consecutive run below the threshold. The default 3 does not change the 50% rule; it waits for three final daily peaks so one or two cloudy days at the end cannot trigger a cutoff. No later day may reach the threshold

env_min_lux and env_max_lux appear separately under Light plots. They are not sensor tests or environmental expectations: they only set the fixed-scale qualification product. The default maximum is 200,000 lux: it covers every finite qualified value in the current archive (maximum 198,401.3 lux) while using the vertical space more effectively than the 320,000-lux upper measurement range published for the UA-002. Qualification always writes both a fixed-scale product and an automatic-scale companion; Data Visualization starts with automatic scaling unless the operator enables (or has saved) Fixed scale. The automatic product provides detail for submerged deployments whose values occupy only a small part of the full sensor range. The manufacturer describes this channel as a measurement of relative light levels, so its lux values should not be interpreted as research-grade photometry.

The values used are written on the QCS_light_window.svg plot itself, in the log and in QCS_test_report.xlsx — the cutoff is always traceable.

8. Qualification Tests

Processing Flow

  1. Pre-processing (unit corrections, GMT-3)
  2. Range Tests (sensor and environmental)
  3. Spike Tests
  4. Rate-of-Change Tests
  5. Flat Line Tests
  6. (For profiles) Vertical Gradient and Density Inversion Tests
  7. (For HOBO) Light usable window (fouling)
  8. Output generation

The log announces the pipeline in 5 stages (reading → pre-processing → tests → output/reports → plots), which makes it easier to find where a run failed.

Sequential Order of the Qualification Tests

  1. Sensor Range Tests — failure becomes BAD (4) (physically impossible value for the sensor)
    • Temperature, Salinity, Conductivity, Pressure, Dissolved Oxygen, pH, Chlorophyll, Turbidity, PAR, Dissolved CO2
  2. Environmental Range Tests — failure becomes SUSPECT (3) (QARTOD alignment: outside the regional envelope is suspect, since a real extreme event is possible)
    • Temperature, Salinity, Conductivity, Pressure, pH, Chlorophyll, Dissolved Oxygen, Dissolved Organic Matter, Turbidity, PAR, Dissolved CO2
  3. Spike Tests (Spurious Values) — 3-point method
    • Temperature, Salinity, Conductivity, Pressure, pH, Chlorophyll, Dissolved Oxygen, Dissolved Organic Matter, Turbidity, PAR, Dissolved CO2
  4. Rate-of-Change Tests — failure becomes at most SUSPECT (3) (QARTOD: real rapid variation exists)
    • Temperature, Salinity, Conductivity, Pressure
  5. Flat Line Tests
    • Temperature, Salinity, Conductivity, Pressure
  6. Vertical Gradient Tests (Profile data only) — real |ΔV/Δz| relative to the profile's typical gradient
    • Temperature, Salinity, Conductivity
  7. Density Inversion Test (Profile data only)
    • Checks water-column stability: the potential density (computed from T, S and pressure) must not decrease with depth beyond a tolerance (configurable in Settings; default 0.03 kg/m³). An inversion indicates a suspect temperature/salinity pair (flag 3) and implicates both — it is not force-dropped; it only leaves the result if "Remove Suspect Data" is on.
  8. Light usable window (HOBO only)
    • Light fouling (biofouling) test — see the HOBO Data section. It generates the light flag position (Flag_lux).

HOBO files: since the HOBO Pendant measures only temperature and light, only the temperature tests from the list above are run, plus the light window test. These switches, its sensor limits and its statistical thresholds are independent from Seaguard. The environmental temperature bounds remain shared because they describe the expected site, not an instrument capability. The flag string stays short and free of meaningless positions.

Comparing results across program versions: the default criteria are broad and general — a national climatological envelope, valid for the entire Brazilian coast — grounded in the QARTOD/IOOS framework. They can be revised between MAJOR versions of the program (that is precisely what a major version means here), so the same raw file may qualify differently under different majors. Never compare results produced by different major versions — requalify first. What changed in each revision is recorded in the project's changelog/ folder.

9. HOBO Data (Temperature and Light)

QCS qualifies and visualizes data from the HOBO Pendant (Temperature/Light) loggers, in addition to Seaguard. Select Input Type = HOBO in the main window and point to the HOBOware export.

Reading the files

  • Accepts the .xlsx and .csv HOBOware exports, with headers in Portuguese or English (the header row and the delimiter are detected automatically; broken accents are tolerated).
  • Automatic light unit: lux is used directly; lum/ft² (foot-candle) is converted to lux (×10.7639). The output is always in lux.
  • Deployment window from the logger events (Coupler On/Off, Stopped, End of File): rows outside the in-water period and event-only rows are discarded, with a note in the log. Out-of-water readings at the edges are also trimmed by a temperature jump (parameter hobo_edge_temp_tol, with a safeguard against removing more than 10% of the series).
  • Zero light at night is a valid value (never becomes missing); negatives become 0.

Qualification

The temperature tests applicable to a mooring are run (sensor and environmental range, spike, rate of change and flat line — producing Flag_T) plus the HOBO-exclusive test:

Light usable window (fouling test)

With the sensor at sea, fouling organisms gradually cover the logger and the measured light decays — beyond a certain point, it is no longer reliable. The test identifies that point:

  1. The clean-sensor baseline is the highest daily light peak of the first lux_baseline_days days (the max, so a cloudy install day does not lower it);
  2. From the start of the final sustained decline — where the daily peak stays below lux_cutoff_frac × baseline for at least lux_sustain_days consecutive days and never recovers to the threshold before the series ends — the light is flagged BAD (4, unusable). Thus the default 3 is a confirmation period, not another cutoff: it operationalizes “the series no longer reaches 50%” while rejecting a one- or two-day cloudy tail. Light that later recovers above the threshold is kept. The values stay in the sheet until you remove them with "Remove Bad Data";
  3. If, after an earlier below-threshold excursion, the light returns to the threshold on a good share of the following days (~20%+), a warning indicates that the decline is not permanent (possible sensor cleaning, multiple deployments in the same file, or a cloudy period) — review it.

Interactive review: before applying, the program shows the daily light envelope with the proposed cutoff — a click moves the cutoff date, the N key removes the cutoff, Enter/close confirms. The final plot is saved as QCS_light_window.svg in the output folder, with the parameters used written on it.

Limitation: the test identifies one cutoff per file. If the sensor was cleaned and returned to the water in the same file, the recovery warning will fire — it is recommended to qualify each deployment (between cleanings) as a separate file.

Output

The qualified HOBO spreadsheet contains only the measured variables + metadata: Sample number, Datetime, Site, Temperature (degC), Temperature spread (degC) (filled when redundant replicates are combined; empty for single files), Luminosity (lux), Battery voltage (V), Flag, Flag_T, Flag_lux, QCS version. It is saved in the QCS qualified hobo data subfolder (the Seaguard one remains QCS qualified tscp data). HOBO and Seaguard spreadsheets are never combined in the same database.

To visualize HOBO databases (dedicated temperature and light panels with the fouling window shaded), see section 11.

Redundant replicates (2-4 HOBOs)

When two or more HOBOs are deployed together for redundancy, simply select all the files at once with Browse — the Replicates box shows how many were picked (the count is program-determined, no manual choice). Each replicate is qualified independently (its own light-window review) and then combined into a single series, saved to a <site>_<start>_<end>_combined_QLF folder (the individual per-file _QLF outputs are also kept). The method is written to QCS_combine_method.txt in the combined folder, each replicate's QCS_light_window_<replicate>.svg is copied there, and a Temperature series.svg plot shows the combined temperature at a glance (it also draws the replicate-disagreement bars — bar = max − min, centered on the mean — the same visual as the Data visualization HOBO panel). The combined sheet's Flag column is intentionally empty: each replicate ran its own tests, so a combined series has no single per-test flag string — the combined verdicts are Flag_T / Flag_lux, and the column stays only so single and combined sheets share one layout and stack cleanly into a database.

  • Temperature: the mean of the replicates that are acceptable (Flag_T ≤ 2) at each timestamp. Replicates are aligned to the first replicate's timestamps by nearest match within half the sampling interval (redundant HOBOs are never started at the exact same second, but that offset is tiny versus the sampling step, so paired readings are effectively simultaneous — it is a nearest match, not interpolation). The between-replicate spread (max − min) is kept in the Temperature spread (degC) column; when it exceeds 0.5 °C the combined Flag_T is set to SUSPECT (3) — the replicates disagree, which is itself a QC signal. A row covered by a single replicate carries an empty spread: there was nothing to compare, and 0 would read as perfect agreement.
  • Light: the per-timestamp maximum of the non-fouled readings (Flag_lux ≠ 4). Fouling only attenuates light, so the brightest unfouled sensor is the most reliable. The combined light stays good while at least one replicate is unfouled and becomes BAD (4) only once every replicate is fouled — the usable window is extended to the last replicate to foul. Light is not averaged (that would mix clean and fouled sensors).

Disagreement review and recorded decisions

Before averaging, QCS applies the versioned batch/replicate_decisions.csv ledger to the named source file, variable and inclusive time interval. Empty interval bounds mean the whole file. In a combined product, bounds are evaluated on its aligned output timestamps. A temperature exclusion leaves light independent. A reference recommendation is advisory: closing the review does not accept it.

An unresolved temperature disagreement above 0.5 °C lasting at least 24 elapsed hours across at least three consecutive eligible pairs is withheld: the temperature is empty and Flag_T=3. Agreement, a missing pair, or a gap longer than 1.5 sampling intervals breaks the episode. This initial review policy does not identify which sensor failed. Isolated disagreements retain their suspect mean; a single acceptable contributor remains usable with an empty spread.

QCS_replicate_samples.csv preserves diagnostic temperatures and individual flags before optional automatic cleaning, with eligible contributor counts and withheld rows. Episode and decision CSVs document why samples were retained or withheld. QCS_report.xlsx counts the actual combined table; individual reports retain their source identity. Reference diagnostics never restore bad readings to the output.

The clock check

A submerged light sensor must peak near local noon. Before the fouling analysis runs, QCS measures the diurnal phase of the light — the light-weighted mean hour of day, computed on the 24 h circle, and the share of light energy recorded between 06:00 and 18:00. A sound logger scores ~100% on that share; a logger whose clock is 12 h out scores ~0%.

The check runs first because a wrong clock makes every daily light statistic below it meaningless: you cannot measure a light decay on a scrambled time axis. It is a property of the whole series, so it produces a warning and a measurement, not a flag character.

Two distinct failures are named:

  • A 12 h phase shift — the logger was launched with AM/PM swapped, so light and temperature both sit on the wrong half of the day. The prescribed correction is exactly 12 h: an AM/PM mistake is exact antiphase, and the measured peak lands slightly off noon only because cloud and fouling are not symmetric about it. Loggers launched this way have recorded tens of thousands of lux at 21–23 h.
  • A collapsed 12-hour clock — some HOBOware exports (pt-BR locale, times written 04h0min0s) carry a 12-hour clock with no AM/PM marker at all, so every afternoon reading lands on top of its morning twin. The signature is no sample after 12:59 plus about half the timestamps duplicated. QCS reports this without prescribing a shift, because the remedy is different: the afternoon half must be reconstructed from the row order, not moved.

A heavily fouled logger is not accused: fouling attenuates the light, it does not move the peak.

The fixed light-cutoff mode

The adaptive fouling rule reads the decline out of the light itself — which entangles it with everything else that moves light on those timescales, season above all. At the Abrolhos latitude the clear-sky ceiling falls to ~60% of its summer value in winter, uncomfortably close to the 50% fouling threshold: a logger installed in March walks into winter and its falling ambient light can masquerade as fouling (over-cutting), while a logger installed in September walks into summer and the rising light can mask real fouling (under-cutting).

The Light cutoff choice in the Qualification tab (HOBO only) offers the deliberate alternative:

  • Reviewed (adaptive) — the default: the fouling decline is detected from the light and the proposed cutoff is reviewed on a plot (drag to adjust, N for no cutoff). Each daily peak is first divided by the astronomical clear-sky curve for the run's latitude (taken from the region selection, which is therefore enabled for HOBO too), so the decision runs on "fraction of the seasonal ceiling" rather than raw lux — a deployment walking into winter is no longer read as fouling, and one walking into summer no longer hides it. On the review plot the baseline and threshold appear as curves that follow the season. The correction removes only the deterministic part of the confound (winter cloud and turbidity remain), which is why the fixed window below exists.
  • Fixed window — light becomes BAD a fixed number of days after deployment (lux_fixed_days in Settings → Parameters, default 60), with no data-driven decision and no review. Fouling on these reefs is well advanced after two months in the water; the fixed window trades the adaptive rule's precision for uniformity and immunity to the seasonal confound. A deployment shorter than the window has nothing to cut. The saved QCS_light_window.svg still shows the daily light peaks and what the adaptive rule would have proposed, and states the fixed rule that was actually applied.

The replicate referee

Averaging is the right answer only while both loggers work. When one sensor is broken, the mean is contaminated and the SUSPECT spread flag does not repair it — and discarding the suspect rows would throw away the sound replicate too. Worse, a sensor stuck on a plausible temperature passes every test that looks at one series in isolation.

So, before combining, QCS runs a referee. It first checks whether the replicates genuinely disagree (more than 0.5 °C over at least 20 % of the overlap). If they agree, nothing changes — they are averaged as before. If they disagree, the referee calls an independent witness: the contemporaneous loggers at other sites. Regional temperature moves together, so a sound logger follows that signal and a broken one does not. Each replicate is scored on three criteria:

  1. Change-correlation with the reference — correlation of day-to-day changes, not absolute values, so a legitimate depth offset does not decide it. This is the primary criterion.
  2. Offset drift — a bias against the reference that shifts during the deployment indicates a drifting sensor; a real site offset stays put.
  3. Seasonal amplitude — the replicate's swing versus the reference's: far too damped, or far too exaggerated, is wrong.

Criteria 2 and 3 measure a replicate against the reference, so they only apply when the reference genuinely tracks this site (change-correlation ≥ 0.70). Otherwise the referee abstains rather than arbitrate with a bad yardstick.

The referee does not apply a fixed seasonal rule such as "warmer in summer". Encoding the expected answer and then keeping the data that matches it is confirmation bias, and it would silently erase genuine anomalies such as a marine heatwave. The reference is measured, contemporaneous and independent; the expectation is never hardcoded.

When a replicate is named, the run pauses and shows the evidence — both replicates plotted against the reference, the score table, and the verdict in words. You choose Accept (qualify from the named replicate alone; the dropped one is recorded in the product's provenance with the full reason) or Keep all (average both). Nothing is ever dropped silently: with no reference available, or with the replicates too close to separate, the referee reports that it cannot decide and the run averages as usual.

They answer three different questions about the same deployment. Every panel omits cells flagged BAD; manually dismissed measurements are blank, and Remove dismissed data may remove their rows entirely. Reading the blanks

Blank heatmap areas can reflect native invalidity, a QCS test, dismissal or absent values. The native Cell state, Cell state 2 and Record state are retained. Native warnings produce SUSPECT; invalid velocity solutions produce BAD. One unavailable beam can remain SUSPECT only with AutoBeam replacement configured; multiple unavailable beams are BAD. Missing or unmapped native quality cannot certify GOOD: an unevaluated signal position makes the current rollup SUSPECT. An unreviewed manual position alone does not. The native map follows Aanderaa TD304 (June 2024), sections 7.3–7.4; translating its warnings into QCS severity is the QCS policy. Speed, strength, standard-deviation and tilt thresholds remain independently applicable.

Requalify older Doppler products. v14.0.1 corrects record decoding, configured coordinates and native-status interpretation, so it changes current QC results. Regenerating figures alone cannot repair an older qualified table. Structural decoding errors now stop the reader; legitimate partial records remain explicit.

To distinguish cases, inspect the qualified row: Flag_cur = 4 means an automatic test rejected a cell that is still traceable in the table; Flag_cur = 5 means the operator dismissed it. If a whole instant has no row, either the raw record was absent or Remove dismissed data removed it; comparison with the raw timestamps settles which. Grey horizontal bands can be depth cells outside the usable acoustic range, while a grey vertical band means that one instant failed or is absent across depths.

12. Curated Database

The Curated Database tab builds a traceable subset directly from the qualified corpus. It does not run quality tests again and never writes into the corpus. On a field computer, enable View > Field mode to disable this tab while leaving Data Qualification and Data Visualization available; the choice persists until it is turned off. Select the folder that contains SEAGUARD\qualified and HOBO\qualified, then choose Load catalog. The scan reads each *_QLF.csv/*_QLF.xlsx product below those two qualified trees; raw files and report spreadsheets are not cataloged. The progress bar remains empty with Calculating... while discovering files, then Catalog 0/N and the current read position, without an indeterminate full-bar animation. It reads neither _EXPERIMENTOS, _PISCINAS, nor direct site folders whose names begin with PISCINA_: those experiment and pool deployments are outside the monitoring corpus and are ignored even if such a folder is restored later. It reads each qualified product's Site and Datetime columns so the filters describe the data itself; a prebuilt qualified_index.csv is not required.

During Build curated database, the bar is cleared before it becomes visible, then starts at Stage 0/N Preparing. Stage 1 applies the selection, one stage is counted for each selected instrument family, and the final stage completes the workbook. Very fast stages may advance before the window's next redraw, so the visible number can skip ahead without any work being omitted. The bar remains below 100% while that workbook is being written and reaches Stage N/N Complete only after the atomic output file has finished.

Selection

Any combination of site, calendar year and instrument can be selected. Each list has All and None shortcuts. Clicking anywhere on an enabled option row toggles its checkbox; clicking the checkbox itself has the same single-toggle behavior. The three lists are dynamic: options that do not occur with the current combination remain visible but turn gray and are automatically unchecked. Broadening another filter makes compatible options selectable again, but never silently restores a previously hidden check. Instruments are ordered as Seaguard (Mooring), Seaguard (Profile), Seaguard (Doppler), then HOBO. Scalar collection type comes from exact product provenance and the explicit QCS collection token in its name. Conflicting evidence is reported; an unidentified scalar product appears as Seaguard (Unspecified) when present, rather than being assigned to Mooring. The matching-product line is a quick catalog estimate; exact row counts are reported after the workbook is built.

Year means the Datetime year. It is not inferred from the campaign semester in the folder or product name. If a deployment crosses New Year, selecting one year includes that product but writes only the rows whose Datetime belongs to the selected year.

Workbook structure

The output is one .xlsx workbook. Its data remain scientifically explicit:

  • Each selected category gets its own sheet: Seaguard (Mooring), Seaguard (Profile), Seaguard (Doppler) and HOBO. Scalar profiles and moorings share a measurement layout but remain separate collections. Incompatible instrument layouts are never stacked.
  • Included products records the campaign semester, corpus path, full data interval, collection type, source-row count and selected-row contribution of every product.
  • Read me records the QCS version, generation time, selected filters, output counts, structure and flag-code legend.

Within each instrument layout, products are merged by the same build_database() engine used by Data Visualization. Exact duplicate rows are removed with a warning; rows sharing Site and Datetime but carrying different values are kept and listed as a possible overlap. Scalar rows are then partitioned into their proven collection sheets. The output folder and name are remembered for the next session. If that filename already exists, the app asks before replacing it. A selection representing at least 250,000 source rows is identified as large in the Selection summary; before building it, the app reports its product and source-row counts and asks whether to continue because processing may take several minutes and the interface may respond slowly. Until every requirement is met, a short message below Build curated database states the next required action. During the build, the standard status-bar indicator reports selection, one unification stage per included instrument, and workbook writing. Cancel is available while loading/refreshing the catalog and while building; it replaces the prerequisite hint while work is active and stops at the next safe checkpoint. The other workflows and window close action stay locked until the worker finishes. A canceled write deletes its temporary file and never replaces an existing workbook, so no partial output is presented as complete.

After a successful build, Open output folder and Go to visualization appear below the build button. A workbook containing more than one collection asks which collection to visualize; Data Visualization then opens that exact sheet directly on Step 2 and uses its proven Mooring/Profile/Doppler/HOBO type. The animated Windows loading cursor appears throughout workbook loading and panel generation, then returns to the normal pointer; selection dialogs remain interactive. Opening the workbook directly exposes the same collection selector on Step 1. Legacy Seaguard/Doppler/HOBO sheets remain readable; explicit source-product names can recover their scalar collection types. An unknown or mixed scalar table requires an editable type choice instead of inheriting a saved Mooring setting. For a mixed table, plots use the matching known collection and report excluded rows. Loading or refreshing the catalog hides shortcuts left by the preceding build because that workbook belongs to the previous catalog state.

For Data Qualification

14. Running from Source Code

Besides the installed program (section 2), QCS runs directly from the Python scripts — the development workflow: any change in the scripts takes effect immediately, with no need to rebuild or reinstall.

Requirements

  • The project folder (containing the sourceCode subfolder and the QCS.bat shortcut)
  • Python (Anaconda is recommended)
  • The project dependencies — numpy, pandas, matplotlib, scipy, openpyxl, gsw and optionally sv-ttk for the modern theme (without it the interface falls back to the classic look) — installed with: 
    python -m pip install -r sourceCode/requirements.txt

How to run

The recommended way is via the QCS.bat shortcut in the main folder, which already calls the correct Python and opens the unified app. Alternatively, in the sourceCode folder, you can run the scripts directly:

python QCS_QtApp.py         # unified app (three tabs) - the normal entry point
python QCS_Main.py          # qualification tool only (development)
python QCS_DatabaseView.py  # visualization tool only (development)

Quick check (self-tests)

To confirm the qualification functions are intact after a change, run in the sourceCode folder:

python QCS_SelfTest.py
